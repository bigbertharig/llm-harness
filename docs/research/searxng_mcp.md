# SearXNG MCP search tool

`mcp_servers/searxng/server.py` is a standalone stdio MCP server for live SearXNG search. It uses only the Python standard library. It does not depend on the `llm_orchestration` checkout or any particular harness or model. Any MCP-capable harness can launch this command and expose its `search_web` tool; the comparison runner uses its own Python interpreter for this backend rather than the older DuckDuckGo helper's virtual environment.

Set `SEARXNG_URL` in the server process environment to the SearXNG instance root, for example `http://127.0.0.1:8888`, or its `/search` URL. For harnesses that do not preserve the runner environment in an MCP child process, pass `--endpoint URL` after the optional receipt path; this takes precedence over the environment variable. The instance must allow JSON output (`format=json`); [SearXNG's Search API documentation](https://docs.searxng.org/dev/search_api.html) notes that requesting a disabled format returns HTTP 403. The URL is not exposed in MCP responses or logs. With no configured URL, the tool remains discoverable and returns a clear configuration error on call.

Launch with `python3 /home/bryan/llm-harness/mcp_servers/searxng/server.py`. Register that command as an MCP server and expose its `search_web` tool. The model facing arguments are `query` (3 to 300 characters) and optional `max_results` (1 to 10, default 5). The result has distinct HTTP(S) URLs in search rank order, short titles and snippets, source engines and published timestamps when supplied, counts, backend latency, HTTP status, and rate-limit and degraded-search signals. It also carries bounded query suggestions, corrections, and unresponsive-engine reasons when the backend returns them. A 429 response carries a bounded `retry_after_seconds` when the server provides a numeric `Retry-After` header. A 403 reports JSON-format denial or access denial without guessing which occurred.

The server makes one HTTP request per call with a 15 second timeout and a 2 MB response limit. It removes URL fragments and duplicates, and caps titles at 180 characters and snippets at 320 characters. It does not fetch result pages, cache responses, or retry; the calling harness should decide pacing and retries. An optional first command argument names a JSONL call receipt. This receipt records tool arguments, URLs, counts, latency, HTTP status, and errors without recording the configured endpoint.

## Harness comparison lane

`tools/comparison_web_search.py` accepts `--backend searxng`. For example, with `SEARXNG_URL` set, run `python3 tools/comparison_web_search.py pi --run-id my-searxng-trial --backend searxng --case python_taskgroup`. The default remains `ddg`. SearXNG case artifacts go under `results/<run-id>/searxng/<candidate>/<case>/`; DDG keeps its existing `results/<run-id>/<candidate>/<case>/` layout. Both fixture and summary label the backend.

The runner first calls the selected MCP server directly. It launches the candidate only when that baseline returns at least five distinct URLs, an expected official domain in the top five, and no rate limit signal. The candidate receives the same server command and `search_web` tool. A failed baseline leaves a per-case receipt with the failed gate and does not call the candidate. The SearXNG lane requires `SEARXNG_URL` in the runner environment; a missing value stops at argument validation.

## Verification

Run `python3 -m unittest -v tests/test_searxng_mcp.py` from the harness root. The local fixture checks MCP discovery and call framing, JSON query parameters, result normalization and cap, provenance and search-health metadata, invalid arguments, missing configuration, and HTTP 403/429 handling. A passing fixture demonstrates the tool contract; it does not establish live SearXNG availability, search relevance, or rate limit behavior on a real instance.

For live research trials, configure an endpoint first. Use the existing `tools/search_provider_benchmark.py --backend searxng --out ...` as the provider relevance and pacing baseline, then run direct MCP calls before candidate harness tests. Record the endpoint availability, query set, counts, status, and rate limit signals in the run receipt. Do not treat the local fixture as live coverage.

## Research and upgrade decisions

- The [current Search API](https://docs.searxng.org/dev/search_api.html) supports query, category, language, page, and time-range parameters. [Search syntax](https://docs.searxng.org/user/search-syntax.html) also lets the model choose supported engines or categories with `!` modifiers. We retain the small `query`/`max_results` schema until a live instance shows that more filters improve relevance without reducing URL yield.
- SearXNG's [JSON response source](https://github.com/searxng/searxng/blob/master/searx/webutils.py) includes ordered results, suggestions, corrections, and unresponsive engines. The MCP now preserves bounded versions of these fields and result engine provenance. A zero-result response with reported engine failures is a typed tool error; usable partial results remain available with `degraded=true`.
- The [official server settings](https://docs.searxng.org/admin/settings/settings_server.html) and [limiter documentation](https://docs.searxng.org/admin/searx.limiter) explain instance-side bot and IP limits. A [maintainer discussion](https://github.com/searxng/searxng/discussions/3655) reports 429s from bot detection for API clients; community MCP [troubleshooting notes](https://github.com/ihor-sokoliuk/mcp-searxng/blob/main/docs/troubleshooting.md) warn that a healthy page or `/config` endpoint does not prove usable JSON search. The MCP reports 403, 429, `Retry-After`, and engine-level failures distinctly and does not automatically retry a denied request.
- A later pool of several operator-controlled SearXNG instances could improve throughput and availability. Keep this `search_web` contract stable and add per-instance health, concurrency caps, cooldown on 429, result deduplication, and receipts behind it. Test latency and relevance on each instance first; more IPs do not guarantee a faster single query, and instance selection should respect upstream limits.

## Three-minute recovery and alternate engines, 2026-11-04

A fresh single-query preflight still returned zero URLs with a rate-limit signal (`results/searxng_recovery_preflight_2026-11-04.json`). The existing provider runner now supports `--pace-seconds` and writes a progress receipt after every query. Its complete four-question run with `--rounds paced --pace-seconds 180` took nine minutes between first and last query and returned HTTP 200, zero URLs, and Google CSE `too many requests` or suspended-engine signals on all four (`results/searxng_spaced_recovery_2026-11-04.json`). Three-minute pacing did not restore this engine during the observation window. Do not treat HTTP 200 or a low response latency as a successful search when the engine reports failure.

The instance's `/config` listed Google CSE and Wikipedia as its enabled general web engines. An engine-specific Bing probe, made after a three-minute gap with SearXNG's `!bi` query prefix, returned ten URLs and no rate signal, but the expected official Python documentation ranked seventh, below this suite's top-five relevance gate (`results/searxng_fallback_bing_2026-11-04.json`). A Qwant probe after another three-minute gap with `!qw` returned zero URLs with a CAPTCHA signal (`results/searxng_fallback_qwant_2026-11-04.json`). These single-query probes establish only availability and one relevance result; neither is accepted as a replacement provider yet. No live engine settings were changed. A fallback needs the full four-query relevance gate plus spaced repeat and health checks before harness comparisons resume.

## Paused after provider limits, 2026-11-04

Live SearXNG rate and concurrency testing is paused. Google CSE returned no URLs with engine-level rate-limit or suspension signals on four queries spaced three minutes apart. Bing returned ten URLs in one alternate-engine probe but missed the suite's top-five official-domain gate; Qwant returned a CAPTCHA. The standalone MCP and deterministic harness fixtures remain useful and tested, but current live-provider results do not establish sustained availability or throughput.

When revisiting, first run a low-volume recovery check and a four-query relevance gate for any fallback engine. If upstream limits remain tied to a shared egress path, consider separately operated SearXNG instances with genuinely independent network egress and per-instance health, cooldown, and concurrency controls. Multiple instances on the same public IP would not create independent IP capacity; more IPs are a possible future experiment, not a proven fix or a basis for claiming higher throughput. Preserve provider limits and avoid repeated requests to an engine reporting suspension. Harness testing now moves to subagents and delegation while live search is paused.
