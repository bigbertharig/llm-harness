# First candidate trial: Codex, then DeepSeek setup check

Date: 2026-10-28
Status: rough live observations; no comparative grade yet.

## Fixed resource

The Pi gateway offered `gpu-rig/chat-27b`, backed by `qwen3.6:27b` on GPU0 at an actual 65,536-token context. Gateway commit `e08271e` added a read-only, ready-only `/v1/responses` passthrough because this Codex version uses the Responses API and the loaded llama-server supports it. The rig roster remained the same after all trials. The CLI tested was the Pi's installed `codex-cli 0.147.0`; `~/codex` is a separate pinned source checkout at `7389eebf45`, so these results apply to the installed binary.

An isolated Codex home supplied a custom provider with `base_url = "http://127.0.0.1:8080/v1"`, `wire_api = "responses"`, `http_headers = { "X-Require-Ready" = "true" }`, `model_context_window = 65536`, and no OpenAI authentication. Trials ran in a disposable workspace with a read-only sandbox and no approvals. The first unisolated attempt reached the model but also tried to refresh a pre-existing login and contact unrelated MCP services; isolation removed that noise. Raw event traces and stderr remain in the ignored `results/codex_smoke_2026-10-28*` and `results/codex_two_turn_2026-10-28/` directories on the Pi.

At this first smoke stage, no compaction, output-budget, long asynchronous job, guardrail denial, or multi-model delegation case had been run. This confirmed a Codex tool loop and durable session on one local model, not a candidate ranking. Later compaction probes are recorded below.

## Measures suggested by this trial

Keep case-level observations before choosing weights or a winner:

1. **Task result:** correct final answer, tool result used correctly, no duplicate tool execution.
2. **Continuity:** same session after restart, key facts retained, visible compaction behavior under pressure.
3. **Resource discipline:** uses only ready routes, stays within served context, accounts for output headroom, never initiates a model load.
4. **Efficiency:** input tokens, uncached prompt tokens, cache reuse, model calls, avoidable retries, and elapsed time per case.
5. **Control and observability:** enforceable permissions, approval behavior, complete event trace, useful failure reason, and asynchronous job wake-up without model polling.
6. **Integration cost:** candidate patches, gateway changes, required adapter/config code, installation effort, and behavior with our small and large models.

For each case, compare candidates on the *same prepared model*, input, tools, and limits. Record unsupported cases and setup failures separately from incorrect agent behavior. A small model's mistaken answer does not by itself prove the harness is poor; a missing trace, unbounded retry, or cold load is directly attributable to harness/integration behavior.

## DeepSeek MCP and compaction probes

**Local MCP (stdio):** an isolated MCP SDK fixture exposed `read_marker`, generated a fresh random marker only when called, and wrote a call receipt. The first profile patch incorrectly targeted a nonexistent entry without `insert`; `--dump-config` printed `entry "mcp-local-fixture" not found` to stderr but exited 0. With the MCP tool absent, the model used file and shell tools to read the fixture source and answered a static marker, so that attempt failed the MCP criterion. The corrected insert patch mounted the server. DeepSeek called `mcp__localfixture__read_marker` exactly once, its tool result matched the server's random marker, and its final answer repeated it. Preserve both traces under ignored `results/deepseek_mcp_2026-10-28/`; the failed attempt is `events_local_initial_failed.jsonl`.

**Public MCP (Streamable HTTP):** the same headless profile connected to [DeepWiki's documented public MCP](https://docs.devin.ai/work-with-devin/deepwiki-mcp) at `https://mcp.deepwiki.com/mcp`, listed its resource and template catalogs, called `mcp__deepwiki__read_wiki_structure` for the public `modelcontextprotocol/servers` repository, and answered with a topic from the returned structure. The Pi's direct outbound connection failed; this probe used a temporary SSH reverse tunnel and workstation HTTPS proxy, both stopped afterward. The 2026-10-29 [cloud MCP trial](cloud_mcp_candidate_trial_2026-10-29.md) traced that failure to the rig Ethernet default route, corrected the route, and passed direct Pi HTTPS MCP tests. This validates DeepSeek's HTTP MCP client through that path, not direct Pi Internet access or authentication. The JSONL and stderr receipts are in the same ignored MCP directory. Neither MCP probe changed the ready roster.

**Automatic compaction mechanics:** a separate four-turn headless session kept the true ready model context at 65,536 and output cap at 1,024. To force a short mechanics test, the profile set `thresholdRatio: 0.17`, `headroomTokens: 2048`, `retainRatio: 0.04`, and summary `maxTokens: 512`. The conversation established codeword `amber-birch-17`, owner Mira, deadline Friday; corrected the owner to Nora and deadline to Tuesday; added routine distracting notes; then asked for current facts. All four turns completed, and the final answer gave Nora, Tuesday, and the unchanged codeword. The compressed durable session log contains two complete `compaction/start` → `compaction/summary` → `compaction/end` transactions, on turns 3 and 4. The second summary explicitly retained the corrected facts. Raw prompts, per-turn events, policy patch, and session log are under ignored `results/deepseek_compaction_2026-10-28/`. The ready roster was unchanged. This proves an early-trigger compaction path and fact retention in this case; native default policy, real 65K boundary behavior, overflow recovery, and restart after compaction remain untested.

## Codex and DeepSeek compaction comparison

Both candidates used the same externally ready `gpu-rig/chat-27b` route, actual 65,536-token context, isolated empty workspaces, and a ready-only gateway header. The keyed facts were codeword `amber-birch-17`, initial owner Mira and deadline Friday, then a correction to owner Nora and deadline Tuesday. Raw prompts, traces, configurations, and persisted sessions are in ignored Pi result directories listed below. The ready roster was unchanged after the runs. The DeepSeek route patch caps output at 1,024 tokens; the Codex provider config does not set an equivalent output cap, so this is a matched transcript and model, not a fully controlled output-budget comparison. These are exploratory single runs, not a scored harness ranking.

**Codex mechanics, shortened trigger:** `results/codex_compaction_2026-10-28/` used installed Codex CLI 0.147.0 with the standard rig provider and a `model_auto_compact_token_limit=14000` override only for this mechanics case. All four turns exited 0. The durable session recorded two `context_compacted` checkpoints. The final answer correctly gave Nora, Tuesday, and `amber-birch-17`. The `codex exec --json` event stream did **not** emit a dedicated compaction item; the checkpoints were found in the persisted session log. The probe script's CLI compaction-event counter of zero therefore does not mean no compaction happened.

**Native defaults on a matching longer transcript:** `results/codex_default_compaction_2026-10-28/` and `results/deepseek_default_long_2026-10-28/` used identical user turns, including 950 and 500 routine-note lines to approach the 65K boundary. Codex had no compaction override; its source computes the automatic limit as 90% of configured context when no explicit limit exists. It recorded one `context_compacted` checkpoint on the final-question turn, and the checkpoint text preserved Nora, Tuesday, and the codeword. However, that turn's final assistant message was only `ACK`, so it **failed the immediate-answer assertion** despite exit 0. A sixth turn in the same resumed thread, asking explicitly for the three values, returned them correctly. This is evidence of retained state but imperfect turn behavior; a repeat is needed to measure reliability.

DeepSeek used the packaged `compaction-basic` policy without any compaction patch. The route patch supplied only the required provider, served context, ready-only header, and 1,024-token output cap. Its fourth turn processed about 60,605 cumulative tokens, emitted only `ACK`, ended with `max-tokens`, and exited 1. A subsequent final-question turn in the same session emitted only `The`, also ended with `max-tokens`, and exited 1. The compressed durable log has zero `compaction/` transactions. The package's default `headroomTokens` is 65,536, and its trigger is `floor(min(W × 0.8, W − O − B))`. With this route's `W=65536`, `O=1024`, and `B=65536`, `W−O−B=-1024`, so its documented proactive policy cannot resolve a positive trigger. Its source says automatic compaction skips such a target and leaves overflow recovery available. No recovery transaction occurred in this run; the observed finish reason was `max-tokens`, not a confirmed context-window overflow. The earlier tuned DeepSeek mechanics pass remains valid but must not be reported as a default-policy pass.

A shorter four-turn DeepSeek default-policy baseline in `results/deepseek_default_compaction_2026-10-28/` completed and answered the three facts correctly. It did not reach pressure and logged no compaction. That establishes ordinary conversation continuity, not native compaction behavior. The matching long case above is the useful default-policy comparison.

**Interpretation:** Codex demonstrated automatic compaction on this local 65K route with its default threshold, but the first post-compaction answer was wrong. DeepSeek's shipped policy needs a per-route headroom adjustment to make proactive compaction usable on a 65K model; keep that adaptation in a separately labeled tuned run. Neither candidate has yet passed a repeated true-boundary correctness case, overflow recovery, or restart-after-compaction test. The DeepSeek dependency footprint remains a setup-cost finding; no packages were removed or settings simplified for this comparison.
